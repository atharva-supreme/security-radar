# Security Radar

Automated dependency vulnerability monitoring for every project in the SupremeOpti organisation.

A scheduled scan reads every lockfile in every repository, on `main` and `staging`, checks every package in them against vendor security advisories the minute those are published, and writes the result to `report.json`. A Claude Code routine reads that file every morning and sends the email and Slack message. This repo does the finding; the routine does the telling. Advisories only: a new package release that fixes nothing is never reported.

Why not `pnpm audit`, Dependabot or OSV alone: they all read the GitHub Advisory Database, which lists an advisory only after GitHub's curation team has reviewed it. Measured on the Next.js releases of 22 Sep and 14 Oct 2026, that review took 8 days each time. The maintainers' own repository advisory, which this scan reads first, is live the same minute as the fix.

## Scope is the watchlist, nothing else

`watchlist.json` is the only place scope lives, and `scripts/discover.mjs` fills it:

| Key | Meaning |
| --- | --- |
| `org` | the GitHub organisation to walk |
| `branches` | branches to scan on every repo when they exist (today `main` and `staging`); the repo's default branch is always included |
| `exclude` | regexes over `repo/path`; matching lockfiles are skipped (vendored plugins, third-party themes) |
| `tooling` | regexes over `repo/path` that mark a lockfile as build tooling rather than a deployed app, on top of the built-in rule (anything under `wp-content/`, `migration/`, `scripts/`, `config/`, `starter/`) |
| `repos[]` | one row per lockfile: `repo`, `lockfile`, `packageJson`, `label`, `kind` (`app` or `tooling`), `branches`. Regenerated by discovery; a row with `"manual": true` is kept as written |
| `feeds[]` | RSS/Atom feeds for runtimes that are not npm packages (Node.js) |

Run `npm run discover` (or the workflow with `discover` ticked) after adding a repository to the organisation or moving a lockfile. It prints what it added and removed. Every package in every listed lockfile is checked; there is no package list to maintain.

**app vs tooling.** A WordPress theme's `package-lock.json` holds gulp and sass, which run on a developer's machine, never on the server. Those lockfiles are scanned too, but the report keeps `kind: tooling` apart and the routine summarises them in one line so they cannot drown the apps that serve traffic.

## How a scan works

Once a day at 08:00 IST, an hour before the routine sends the report at 09:00, the `watch` workflow runs `node watch.mjs`, which:

1. Reads every lockfile on every listed branch: all installed versions, which of them the app declares directly, and the Node.js version it declares.
2. Queries OSV.dev in batches for every distinct package@version (reviewed advisories plus malicious-package records). New or changed advisories are fetched once and cached in `state.json`.
3. Looks up each package's GitHub repository on the npm registry (cached in `packages.json`) and reads that repository's own security advisories. Requests are conditional, so a repository with no new advisory costs nothing against the rate limit.
4. Fetches the Node.js vulnerability feed.
5. Matches: OSV answers per exact version; repository advisories are matched by range. An advisory the maintainers have published that OSV does not yet return is marked **early**, the window in which every other scanner says "clean".
6. Confirms each fixed version is on npm, and writes `report.json`, `state.json` and `packages.json`, then commits them. The git log is the audit trail.

## report.json

| Field | Meaning |
| --- | --- |
| `status` | `RED` (an open critical or high anywhere), `AMBER` (moderate or low only), `GREEN`, `UNKNOWN` (a lockfile or a source could not be read; see `errors`, `warnings`) |
| `summary` | totals: open, distinct, by severity, malicious, newOpen, early, oldestCriticalOpenDays, newNotAffecting |
| `projects[]` | one row per repo and branch, worst first: `status`, `appStatus` (apps only, tooling ignored), counts, `apps`, `affectedApps` |
| `advisories[]` | one row per distinct open advisory, worst first: severity, summary, url, fixed, `early`, `isNew`, and `hits[]` (every app it affects with the installed version), `apps`, `projectBranches`, `projects` |
| `apps[]` | one row per lockfile per branch: `project`, `branch`, `label`, `kind`, `open[]` (each with `direct`, `early`, `openDays`, `fixedOnNpm`), `upgrades[]` (with `transitive` versions and `worst`), `notes[]` (what `pnpm up` cannot move and why), `command` |
| `newNotAffecting[]` | advisories first seen in the last 26 hours that hit nothing installed |
| `checked` | packages, pairs, reposPolled, projects, apps, appKinds, sources |

`isNew` means first seen within the last 26 hours. An advisory met for the first time more than a week after publication is dated by publication, so adding a repository does not flag its history as new.

## Setup

1. Repository secret `REPO_READ_TOKEN`: a token that can read every repository in the organisation (a classic token with `repo`, or a fine-grained one approved by the organisation). Without it the apps show as `UNKNOWN`.
2. The schedule is on. `Actions > watch > Run workflow` runs it by hand; `dry_run` shows the report without committing; `discover` rebuilds the watchlist first.
3. The Claude routine clones this repo and reads `report.json`. It needs the Claude GitHub App installed on this repository.

## Running locally

```bash
export GITHUB_TOKEN=$(gh auth token)   # a login that can read the lockfiles
npm test
npm run discover -- --dry-run          # what the watchlist would become
npm run dry                            # full scan, writes report.json only
```

The first scan looks up every package on npm once and polls every repository without a cached ETag, so it takes several minutes. Later scans are mostly conditional requests.

## Files

| File | What |
| --- | --- |
| `watchlist.json` | Scope: org, branches, exclusions, tooling rules, the lockfile rows discovery found, feeds |
| `scripts/discover.mjs` | Walks the organisation and rewrites `watchlist.repos` |
| `state.json` | Every advisory seen (trimmed), ETags per repository, feed items. Committed by the workflow; edit only via `--forget` |
| `packages.json` | npm package -> GitHub repository, cached |
| `report.json` | The latest scan result. Committed by the workflow |
| `watch.mjs` | The scan. No npm dependencies |
| `src/` | GitHub client, OSV client, npm registry lookup, semver range check, lockfile readers, feed parser, report builder |
| `.github/workflows/watch.yml` | The schedule and the manual-run inputs |

## What it does not do

- It does not upgrade anything. `report.json` names the fixed version and the command; applying it is a person's job, or a later automation's.
- It does not parse Node.js version ranges from the Node blog. A feed item is reported with the Node version each app declares.
- It does not catch an advisory a maintainer never files anywhere.

# Security Radar

Automated dependency vulnerability monitoring for every project in the SupremeOpti organisation.

A cron job on our server runs once a day at 08:00 IST: it reads every lockfile in every repository, on `main` and `staging`, checks every package in them against vendor security advisories the minute those are published, writes the result to `report.json`, stores the day in MySQL, and posts to Slack: one summary message, one message per affected project with a table of what to upgrade, and one list of the projects that are clear. The messages are built in code (`scripts/slack.mjs`); Claude Code writes only the short opening paragraph of the summary. Advisories only: a new package release that fixes nothing is never reported.

Why not `pnpm audit`, Dependabot or OSV alone: they all read the GitHub Advisory Database, which lists an advisory only after GitHub's curation team has reviewed it. Measured on the Next.js releases of 22 Sep and 14 Oct 2026, that review took 8 days each time. The maintainers' own repository advisory, which this scan reads first, is live the same minute as the fix.

## Scope is the watchlist, nothing else

`watchlist.json` is the only place scope lives, and `scripts/discover.mjs` fills it:

| Key | Meaning |
| --- | --- |
| `org` | the GitHub organisation to walk |
| `scan` | `reported` (today): read only the repositories in `report.projects`, deployed lockfiles only. `all`: read every row, the organisation-wide scan; Slack still posts the reported projects only. Discovery writes every repository into `repos[]` either way, so switching is one word |
| `branches` | branches to scan on every repo when they exist (today `main` and `staging`); the repo's default branch is always included |
| `exclude` | regexes over `repo/path`; matching lockfiles are skipped (vendored plugins, third-party themes) |
| `tooling` | regexes over `repo/path` that mark a lockfile as build tooling rather than a deployed app, on top of the built-in rule (anything under `wp-content/`, `migration/`, `scripts/`, `config/`, `starter/`) |
| `report.projects` | the repositories Slack reports on, with their display names (`"Org/repo": "Name"`). Today the Next.js, Sanity and BigCommerce builds. Every other repository is still scanned and stored, so counts and history stay complete, but it never gets a Slack message |
| `repos[]` | one row per lockfile: `repo`, `lockfile`, `packageJson`, `label`, `kind` (`app` or `tooling`), `branches`. Regenerated by discovery; a row with `"manual": true` is kept as written |
| `feeds[]` | RSS/Atom feeds for runtimes that are not npm packages (Node.js) |

Run `npm run discover` after adding a repository to the organisation or moving a lockfile, and add the repository to `report.projects` for it to be scanned (in `reported` mode) and posted. It prints what it added and removed. Every package in every listed lockfile is checked; there is no package list to maintain.

**app vs tooling.** A WordPress theme's `package-lock.json` holds gulp and sass, which run on a developer's machine, never on the server. Those lockfiles are scanned too and stored in the history, but the Slack messages cover `kind: app` only.

## How a scan works

1. **Read** every deployed lockfile of every reported project on `main` and `staging` (GitHub Contents API). From each lockfile: installed versions, what the app declares itself, and the dependency graph (which declared dependency pulls a package in, and whether it is reachable from `dependencies` or only from `devDependencies`).
2. **Match** every package@version against OSV.dev (batch) and the maintainers' own repository advisories. Where OSV knows a package, its reviewed ranges decide; a hand-typed repository range never adds a hit OSV has ruled out.
3. **Fix versions** come from the advisory data only: the lowest stable fix above the installed version on the same version line (major, or 0.minor). Never a downgrade, a pre-release or another major. A direct dependency with no fix in its line is offered the major bump, labelled as such.
4. **Tier** every (package, version line) per app: **P0** deployed graph, critical/high, fix available · **P1** production but moderate/low, no fix the app can take, or not reachable · **P2** dev-only, or in the owner-editable build-tooling list `watchlist.json → report.toolingPackages`. P2 never reaches Slack, not even by name.
5. **Usage** (`scripts/usage.mjs`): each repository's source tarball is grepped, on every scanned branch separately (main and staging can be hundreds of commits apart), for imports of the flagged packages, for the package named as a string in configs and package.json scripts (`mentions`), and for framework signals (dangerouslySetInnerHTML, "use cache", ImageResponse…). Documentation, built bundles under `public/` and agent tooling folders are skipped. Nothing is cloned or written.
6. **Filter** (`scripts/filter.mjs` + `server/filter.prompt.md`): Claude receives the critical/high candidates of one project with every fact above and decides `now` / `later` / `skip` with a one-sentence reason, plus the summary bullets. It may never change a version or add a package; every line is validated against the report, a critical it did not mention is kept.
7. **Tell** (`scripts/slack.mjs`): one Slack message per project.

## The Slack messages

One message per reported project, lowest overall Health Score first, built in code from report.json and the day's verdicts:

```
📦 VectorLabs · Health Score · staging 79 · main 29 · overall 29 · 🔴 RED
staging · 🟠 AMBER · Health Score 79 · 0 critical, 1 high · 1 package to fix
• web · nodemailer 7.0.13 → 10.1.4 · closes 20 · HIGH · open 220 days · direct · ⬆ major
main · 🔴 RED · Health Score 29 · 1 critical, 1 high · 2 packages to fix
• same fix as staging: nodemailer 7.0.12
• web · next 16.2.12 → 16.4.1 · closes 11 · CRITICAL · open 68 days · direct · fixed on staging
Unused · declared but never used in the code
Out of sync · package.json and lockfile disagree, versions for these packages may be wrong
What to do
• staging · web: cd web && pnpm up -r nodemailer@10.1.4
• main: merge staging, that closes all 2 fixes
P1 · 8 packages for later · P2 · 4 packages, no action
```

**Tiers come from Claude.** Every package with an open advisory goes to the filter, including dev-only and tooling packages. Claude assigns P0 (used by this project and necessary), P1 (later) or P2 (not used, no action); moderate and low can never be P0. The scanner's own tier is only the fallback when Claude could not decide.

**Tiers are stable.** `data/decisions.json` keeps each answer under a hash of its facts (package, line, target, direct, chain, severity, advisory ids, whether the code uses it). The answer is reused until one of those changes, so only new or changed packages cost a Claude call. Editing `server/filter.prompt.md` makes every decision again.

**Staging first.** Staging is always listed in full. main says "same as staging" only when every line matches on target and installed versions; otherwise it names the shared fixes in one bullet with main's own versions and lists what only main has. **Health Score**: RED while a critical P0 is open (at most 59), AMBER while any P0 is open (at most 89), GREEN once P0s are fixed; the P1 backlog costs at most 10 points. Overall is the lower of staging and main.

**Unused** lists flagged packages the app declares whose name never appears in that branch's code; packages a framework loads by name (`report.implicitUse`) are exempt. **Out of sync** lists package.json dependencies the lockfile records differently or not at all, skipping packages a pnpm override rewrites. Versions always come from the lockfile; package.json is only this check. **Who writes what.** Claude produces everything under the header and section titles (`server/message.prompt.md`): package lines, the same-fix comparison, Unused, Out of sync, What to do with its commands, and the P1 and P2 counts. The code calculates the same body independently and rejects any difference, up to three attempts, naming each one. What to do may be worded freely, but its package@version set must match exactly. If Claude still fails, the code's version goes out with a warning. A project with packages to fix normally costs one Claude call a day, because open days change daily.

**History.** `scripts/store-tiers.mjs` runs after the filter and stores `project_health` (scores per branch and overall, same numbers as the Slack header) and `package_tiers` (tier, scanner tier, reason, decision date per package) in MySQL.

## report.json

Schema 4. `apps[]` carries, per deployed lockfile, `open[]` (one row per advisory × package × installed version with `fixed`, `fixedAny`, `direct`, `prod`, `via`) and `upgrades[]` (one unit per package and version line with `to`, `toMajor`, `closes`, `tier`, `reason`). `projects[]` carries the deterministic `health` per branch. The day's verdicts live in `data/verdicts/YYYY-MM-DD.json`, the usage facts in `data/usage/YYYY-MM-DD.json`.

## Setup (server)

1. Clone the repository on the server and run `bash server/install.sh`. It checks node and the claude CLI, installs dependencies, creates `.env` from `.env.example` and stops.
2. Fill `.env`: `REPO_READ_TOKEN` (a token that can read every repository in the organisation; classic with `repo`), `SLACK_WEBHOOK_URL`, `MYSQL_URL` (optional). Run the installer again: it applies `server/schema.sql` when the mysql CLI can reach the database, and installs the cron line for 08:00 IST in the server's own clock.
3. `TZ=Asia/Kolkata ./server/daily.sh` runs the whole day by hand. Logs are in `logs/`, reports in `data/reports/`.

The server is the only copy of the state and the reports; nothing is pushed back to GitHub. The `watch` GitHub Actions workflow is kept but disabled.

`state.json`, `packages.json` and `report.json` are git-ignored: the first scan creates them, every later scan updates them, and a `git pull` on the server never touches them. To update the server, `git pull` is enough.

## Running locally

```bash
export GITHUB_TOKEN=$(gh auth token)   # a login that can read the lockfiles
npm test
npm run discover -- --dry-run          # what the watchlist would become
npm run dry                            # full scan, writes report.json only
npm run slack -- report.json --dry-run           # print the Slack payloads, post nothing
npm run slack -- report.json --only Catalent     # post one project's message, for testing (needs SLACK_WEBHOOK_URL)
```

The first scan looks up every package on npm once and polls every repository without a cached ETag, so it takes several minutes. Later scans are mostly conditional requests.

## Files

| File | What |
| --- | --- |
| `watchlist.json` | Scope: org, branches, exclusions, tooling rules, the lockfile rows discovery found, feeds |
| `scripts/discover.mjs` | Walks the organisation and rewrites `watchlist.repos` |
| `state.json` | Every advisory seen (trimmed), ETags per repository, feed items. Edit only via `--forget`. Git-ignored, created by the first scan |
| `packages.json` | npm package -> GitHub repository, cached. Git-ignored, created by the first scan |
| `report.json` | The latest scan result; one copy per day under `data/reports/` on the server. Git-ignored |
| `watch.mjs` | The scan. No npm dependencies |
| `src/` | GitHub client, OSV client, npm registry lookup, semver range check, lockfile readers, feed parser, report builder, Slack message builder |
| `scripts/slack.mjs` | Posts the messages; `--dry-run`, `--only <project>`, `--narrative-file` |
| `scripts/store.mjs` | Loads one day's report into MySQL (`server/schema.sql`) |
| `server/` | `install.sh`, `daily.sh`, `narrative.prompt.md`, `schema.sql` |
| `.github/workflows/watch.yml` | The old GitHub Actions schedule, disabled |

## What it does not do

- It does not upgrade anything. `report.json` names the fixed version and the command; applying it is a person's job, or a later automation's.
- It does not parse Node.js version ranges from the Node blog. A feed item is reported with the Node version each app declares.
- It does not catch an advisory a maintainer never files anywhere.
